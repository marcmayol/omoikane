# Sync, projects and spaces

[Español](sync-and-spaces.es.md) · [Back to the README](../README.md)

## Sharing memory between computers (and teammates)

Omoikane hosts nothing: it syncs through a git repository of yours, used only for this knowledge (never your code repository). Any remote works: a private repo on GitHub, GitLab, Codeberg, your company's Gitea, or a shared folder. It uses your own git credentials.

```
omoi sync init git@github.com:you/my-memory.git   # on the first computer: asks what to share
omoi sync code                                    # prints a code that carries the key
omoi sync join <code>                             # on another computer (or `--url` to reach it another way)
```

From then on it runs by itself, for every agent: after each saved, changed or forgotten memory, `omoi` syncs in the background (changes a few seconds apart go in one commit), and pulls when a session starts. `omoi sync status` and `omoi doctor` say how the last sync went, the web view shows it too, and a session warns if sync has been failing for over an hour.

What other computers push also arrives in the middle of a session. With each message, if it has been more than 2 minutes since the last look, `omoi` starts a `git fetch` of the repository on the side and doesn't wait for it: when there is nothing new, that is all it does; when there is, it runs a full sync in the background and the new memories show up in the recall of the next messages. With several sessions open only one starts it, and two syncs never run at once. `omoi serve` does the same every 2 minutes while it runs. Without sync set up, nothing happens. `OMOIKANE_SYNC_EVERY` changes the interval (in seconds), and `OMOIKANE_SYNC_AUTO=0` turns it off along with the rest of the automatic sync.

- **What travels:** text, never the database. One encrypted line per memory, in one file per project and per computer, so a change is a one-line diff and nobody's file conflicts with anyone else's. Vectors and indexes are rebuilt on each computer.
- **Encrypted on the remote:** each line is encrypted (AES-SIV) before it leaves your computer; the repository only ever holds ciphertext and opaque folder names. The key is created by `init` and travels inside the join code, so **share the code only through a private channel**. Lose every copy of the key and the remote can't be read, though each computer keeps its own memories.
- **Changing the key:** `omoi sync rotate` (`--space <name>` for a space's repository) re-encrypts this computer's memories with a new key and prints the new code. Computers that only have the old key stop reading what is written from then on: that is how someone who leaves the team or the client stops getting anything new.
- **What is shared** is chosen in `init`/`join`: kinds (preferences stay personal unless you say so), global memories, which projects, and whether each memory carries its author (your git name, on by default). With teammates, their memories show up marked `[by Ana]` so the agent treats them with care.
- **Which version wins:** the newest change by a hybrid logical clock, so a computer with the wrong time can't overwrite newer work. The older local version stays in the memory's history. Forgotten memories don't come back from another computer.
- **Projects** are matched by their git `origin` remote, so the same repo in different folders on different computers is the same project. Projects without a remote are matched by folder name, only between the same person's computers. A project's space travels on its own line, and the newest move wins; `--space` keeps a repository to one client.
- **Computers on different versions:** from 1.0 on, what a new version adds doesn't break the old ones. A field a computer doesn't know is kept with the memory and goes back up even if that computer changes it, so it isn't lost by passing through it. A line of a kind it doesn't know is skipped, `omoi sync status` says "N line(s) from a newer version: update omoi", and after updating everything is read again. And if a version ever changed something the old ones can't read right, the repository says so in `omoikane.format` and the old ones don't write to it until they're updated (`status`, `doctor` and the session start say so).

`omoi sync off` stops syncing on a computer; its memories stay.

## Projects

Memories belong to the git repository you run `omoi` in (`--global` makes one apply everywhere). If you open your sessions in your home folder instead of inside a repository, you see the memories of every project, and a new memory goes to the repository its absolute paths point to (or is global); `omoi update <id> --project <folder>` or `--global` moves one later.

Each project has its key, worked out once: its git `origin`, or, without one, your name and the folder's. It also keeps every folder it lives in, so two clones of the same repository, or a worktree, are the same project. Without an `origin` too: worktrees are recognised by their shared git folder even when their folders have different names (`D:\Kumi` and `D:\kumi-feature`), and the key carries the repository's name. Move the folder of a repository with an `origin` and its memories follow it by themselves at the next session (you're told once); without an `origin`, `omoi projects move <project> <folder>`, and until then `omoi review` and `omoi doctor` point it out. `omoi projects` lists them. `omoi projects merge <a> <b>` joins two without touching ids, history or verdicts, keeping the newer of their two `status` memories; `omoi projects prune` forgets the ones left without memories.

## Spaces: one per client

Spaces keep clients apart. `omoi spaces add acme`, then `omoi space assign acme` in each of the client's repositories (or `omoi projects move <project> --space acme`). From an Acme project you see its memories, the space's and the global ones, never another client's: not in search, not in recall, not in `context`. What is common to all of a client's repositories is saved with `remember --space` (`space: true` over MCP); your preferences stay yours, global. From your home folder you see everything. `search` and `recent` take `project` (a folder or part of a name) and `space`.

To share it, one repository per client, with its own key: `omoi sync init --space acme <url>` carries only that space, without your global memories, and the general repository doesn't carry the space's memories. Preferences saved for the whole space (`remember --space`) are the team's, so they always travel through it, even if you chose not to share preferences; yours (global) never do. The memories of a space are signed with the `--author` of that space's repository, and only those. Join acme as "Ana (Acme)" and that name never shows up on beta's memories or on yours. A CI job or a server joins with the space's code in `OMOIKANE_SYNC_CODE`, without prompts: see [unattended.md](unattended.md).

### Someone new joins a client

`omoi sync join <code>` for a space ends by saying what arrived: how many memories, in which projects, how many pinned and how many open decisions. From the first session in any of those projects, the agent has the space's pinned memories and preferences, as always. The first session in each project on that computer also brings a short welcome, once: the space's other projects with where their work was left (their latest `status`), the decisions still open in them, and who writes in the space. Only that space, never another client's. If everything in the space was written by you, there is no welcome.

### Projects on hold

Moving a project into a space never moves it anywhere else by itself: anyone with a repository's key could write that line. Your other computers find out at their next sync (the general repository only says that a project went into a space, not which one, nor what's in it; the space's repository says which) and put the project **on hold**: nothing of it is uploaded to any repository, and nothing that arrives for it is applied, until you decide on that computer. If you're not sure, `omoi projects keep web` leaves it where it was; `omoi projects move web --space acme --force` accepts the move. Either way it syncs again, and the newest edit wins.

A space's repository can also name a project you haven't opened on this computer yet (a coworker's, or a library of yours that someone uses at the client): the first time you open that folder, the project goes on hold too, and what you save there stays on your computer until you say whose it is: `omoi projects keep <project>` if it is the client's, `omoi space unassign <project> --force` if it is yours (it goes to your general repository, never to the client's). `omoi sync`, `omoi sync status`, `omoi doctor`, `omoi review`, the web view's Review (with both commands to copy) and the agent at the start of each session say so until you decide. So the worst a forged line can do is put a project on hold, never send a client's memories, or yours, to another repository.

`omoi export --encrypt` from a client's project uses that space's key; with `--all`, the general one.

### Overview by client

Whoever runs a client, or the whole factory, opens **Overview** in the web view (`omoi serve --open`). Each space gets three blocks:

- **What there is**: its projects with how many memories, how many pinned and their latest `status` (when and by whom), the open decisions (answered in **Projects**) and what is pinned.
- **Who wrote it**: memories per author (the `author` that sync writes on each memory; "No author" for those saved without sync or with `--no-author`), how many in the last 30 days, when the last one was and with which agents (`mcp:claude-code`, `mcp:codex`, `cli`…), and the latest activity.
- **Outdated or paused**: what Review flags (outdated, superseded, contradicting, due, never used…), the projects on hold with both commands to copy, and the memories nobody has touched in over 3, 6, 12 or 24 months (6 by default).

It follows the space isolation: a server started in a client's project only shows that space (all of it, not just that project), one started in a project with no space only the projects with no space, and one started in the home folder shows every space. Global memories belong to no client and aren't counted. Scripts get the same from `GET /api/overview?months=6`.

## Trades: what one stack teaches, for every project of that stack

A trap like "don't kill the Android emulator with `taskkill`" isn't about one project or one client: it helps every Android project. That's a **trade memory**. Each project has its trades (its stack), worked out from its files at the start of each session, cheaply: the root and one level of subfolders, nothing deeper. `android` (Gradle with Android, an `AndroidManifest.xml`), `web` (`astro.config.*`, `next.config.*`, `vite.config.*`, a `package.json` with a web framework, an `index.html` at the root), `wordpress` (`wp-config.php`, `wp-content`, a theme's `style.css`, a plugin's header), `rust`, `python`, `plugin-claude` (`.claude-plugin/` or a mod's `hooks/hooks.json`), `escritorio-node` (Electron or Tauri: a desktop app, not a web), `alexa` (`skill-package/`, `ask-resources.json`), `node`, `jvm`, `go`, `php`, `ios`, `flutter`, `dotnet`, `docker`… The names are the ones Kumi's production lines use, so there is no table of equivalents. A project can have several, and all of them are listed (Omoikane is `rust` and `plugin-claude`): `context`, `omoi projects --json` and `/api/projects` give the whole list, without picking one. `omoi trades` shows a project's trades and where they come from, `omoi trades list --all` every project's, and `omoi projects` lists them too.

If detection gets it wrong, fix it: `omoi trades add seo-geo` (a trade the files can't tell, like SEO and GEO work), `omoi trades remove docker`, `omoi trades set android kotlin` (exactly these, and stop detecting) and `omoi trades auto` (back to detecting). These corrections stay on that computer: each computer detects its own folders.

Save one with `remember --trade android` (`trade: "android"` over MCP; `update` with `trade` turns a memory into one, and `trade: ""` turns it into an ordinary global memory: it doesn't go back to the project it came from). It belongs to no project and no space: every project with that trade sees it, of any client, in search, recall, `recent`, `context` and the web view, and the rest never do: the agent's `get` and the web view refuse it by id too. A web project of one client doesn't get the Android trap; an Android project of another client does. From your home folder you see them all. The agent is told at session start which trades the project has and when a trap belongs to the trade rather than to the project.

Any kind can be a trade memory, not just traps. Preferences and pinned ones are injected at the start of every session of a project of that trade, with your global preferences, so they apply without anyone saying so: "new screens go in a `Scaffold` and use its padding" as an `android` preference reaches the next Android app from its first session. Procedures, facts and decisions come with recall, as always.

Some only make sense for clients, or only for your own projects. `--for client` (`for: "client"`) keeps a trade memory for the projects in a space; `--for personal`, for the ones in none; without it, both. "When a web is for a client, review the landing's SEO and GEO" as a `web` preference `--for client` reaches every client's web and not your countdown page. There is nothing new to set on a project: being in a space is what makes it a client's.

A memory saved in a project can turn out to be of the trade: `omoi update <id> --trade android` (`update` with `trade`) promotes it. Everything it will carry goes through the same check (text, paths, tags, key and data), so one that names the client has to be rewritten in that same `update` (`-t`, `-c`). What happens next depends on whose it is. A personal memory (a project in no space, or a global one) is moved with the same id, its history and its verdicts: all of that is yours. A client's memory (in a space, or in a project of one) is not moved: a **new** trade memory is created with the rewritten text, a new id, and no history or verdicts (`promoted_from` in the answer says which one it came from), and the client's memory stays where it was, with its history, travelling through the client's repository as before. Its history and verdicts were the client's, and moving it to the general repository left a copy on the client's other computers that sync then refused. If the client's memory now only repeats the new one, forget it yourself.

A trade memory reaches every client, so it can only hold knowledge of the stack. Omoikane checks before saving one and refuses (`trade_leaks`, exit code 2 in the terminal) if the text names a project, a space (a client), an absolute path of yours, the URL of one of your repositories (or any SSH one), the domain of a client's git server, or a domain that only shows up in a client's memories. It looks at the title, the content, the paths, the tags (except the reserved ones: `trade:`, `trade-for:`, `review:`, `open`, `blocking`, `resolved`, `status`), the key and the data (its keys and texts), ignoring case and accents ("balua" is Balùa), and space names from 2 letters. `update` checks what's new in a trade memory (tags and data too, even if that's all it changes), and resolving a trade decision checks the answer. Rewrite it without them, or save it in the project. `force` only skips the duplicate check; for a false positive you have looked at (a library named like a project) there is `allow_leaks` (`--allow-leaks`), which never lets through an absolute path or a repository URL. It's a warning, not a guarantee: it can't know a client's name it has never seen.

Trade memories travel through your general repository only (with `global` sharing on, like global memories), never through a client's, and a client's repository can't bring one in: a line like that is refused. A computer still on 1.7 or older gets them as ordinary global memories, seen everywhere.
