# Changelog

What changes in each version of Omoikane. The release workflow publishes the section of each version as the notes of its GitHub Release, and won't publish a version that has no section here. Every section ends with **Compatibility**: which versions it understands and which ones understand it.

How it works is in [docs/](docs/).

## Unreleased

### The trace in the provenance
- If the agent runs inside a trace (whoever launched it set `TRACEPARENT`, the W3C Trace Context standard that OpenTelemetry uses), each new memory also keeps its `trace_id` and `span_id`. `get` and `history` show `trace <trace_id>/<span_id>`, the web view too, and the JSON carries both in `provenance`. Claude Code passes `TRACEPARENT` on to its shell and to its MCP servers, so an agent factory that opens a span per step gets, from a run's trace, the memories it left, and from a memory, the step that wrote it. They are random ids with nothing of the project, so global memories and a space's own keep them; trade memories don't carry any provenance, as before. A malformed `TRACEPARENT` (wrong length, uppercase, all zeros, version `ff`) is ignored.

**Compatibility**: reads everything 1.0–1.8 wrote. 1.8.5 and 1.8.6 keep the two new fields as they are, except when they trim the provenance of a memory moved to global, which rewrites it without them.

## 1.8.6 (2026-11-08)

### Duplicated trade memories
- `remember` with `trade` now checks for duplicates among the memories of its trades. Before, it compared only with the global memories that aren't trade memories (from the global level no project has trades, so trade memories were hidden), and saving the same gotcha from two clients left it twice. It answers `duplicate_of` as for any memory, and `force` saves it anyway. It compares the new memory with the global memories and with the trade memories that share one of its trades, whoever they are for (`trade-for:`), and only with those: many similar project memories can't push the real duplicate out of the candidates. It is one comparison against those memories, as cheap as any `remember`.
- Promoting a client's memory to a trade (`update` with `trade`) isn't blocked, since the promotion is done, but when the new trade memory says nearly the same as another one of its trade the answer carries `duplicate_of`, `similarity` and `duplicate_hint` (the CLI says it too).
- The review proposes merging two memories of the same trade that say the same thing: *duplicated trade memories* (`trade_duplicate`), in `omoi review`, `context`, the notice at the start of the session and the web view's Review tab, which has the **Merge** button for them as for outdated ones. It uses the same rule as `remember` among the memories of each trade, with the vectors already saved (no model loaded); without vectors, by words, and then each memory has to cover the other. "It's fine as it is" (`omoi review --dismiss <id> --kind trade_duplicate --other <id>`) marks the pair `compatible`, and a pair with any verdict isn't proposed.
- Comparing the memories of a trade with each other is worked out in the background, never while answering: like `code_drift`, it runs in a separate process Omoikane launches and nobody waits for (no daemon or service). It runs in the daily background job (`omoi review --refresh-drift`) and after a write that changes a trade memory (`remember`, `update`, `forget`, a sync or an import), only if none is already running (a lock file next to the database, `<database>.trade-duplicates.lock`). The result is kept in local `meta`. The start of the session, `context`, `omoi review`, the recall and the web view only read it; when there is nothing kept yet they launch the background job and the pairs show up the next time. After a write the calculation is incremental: only the memories that changed since the last one are compared with the memories of their trades, and the words and their weights are worked out once per memory. The daily job compares every pair again, because the weights of the words and the average of the vectors move over time. If a launched calculation dies before keeping its result, the next read or write launches it again after 10 minutes. What is kept can lag behind: before showing a pair, and when pressing **Merge**, both memories are checked to be alive and unchanged since they were compared (their `updated_at`); if not, the pair isn't shown, the web view says so instead of merging, and it is compared again.
- Without vectors, the words weigh with the IDF of the whole database. A first version worked them out in the global scope, where trade memories are hidden: with only trade memories the weights came out negative and no pair was ever found.
- Measured on test databases without a model (release, Windows; 300 and 42 trade memories of one trade with made-up text and one real duplicate pair). The full calculation of 300 takes about 0.2 s (0.42 s for the whole background process, which includes starting and letting go of the lock), and after changing one memory the incremental one is a few milliseconds (0.22 s the whole process, the same as with nothing to compare); 42, a few milliseconds. A first version of 1.8.6 did it while answering, comparing the words of each pair in the index: with 300, `omoi review` hadn't finished after 5 minutes and the start of the session after one. Now the start of the session doesn't change: median of 15 interleaved rounds of `omoi recall --session-start` from a project of that trade, each on a fresh copy of the database (the first start of the day, which counts the review; later ones are faster), 80.1 ms with 1.8.5 and 79.6 ms with 1.8.6 with 300 trade memories, and 73.5 ms and 73.0 ms with 42.

### Trade detection without reading files at every start
- The start of a session no longer reads the project's marker files every time: what was detected is kept per project (in `meta`, local) with a fingerprint of what it depends on (the names in the root and the folders it looks at, and the size, date and cloud state of the files whose content it reads). While it doesn't change, only folders are listed. In OneDrive or a network folder, reading `build.gradle`, `package.json` and the rest at every start was slow.
- A file that is only in the cloud (Windows attributes `RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN` or `OFFLINE`, as OneDrive's Files On-Demand leaves them) is never read: reading it would download it. Its name still counts (`package.json` is still `node`), what it says inside doesn't until it is downloaded, which changes the fingerprint.
- With more than 60 subfolders, the ones looked at depended on the order the system lists them; now they are the first 60 by name, and the entries of each folder are sorted too, so the same files always give the same trades.
- Measured on a test database (41 memories, a project with 72 subfolders, 12 PHP files and Gradle, release, 40 interleaved rounds of `omoi recall --session-start`): median 38.1 ms before, 33.6 ms after.

### The same key from two computers
- `remember --key` is atomic on each computer, but two computers that created the same key at the same level without seeing each other ended up with two memories for it after syncing. Now one rules, the same one on every computer: the one changed last (then the larger id). `get --key`, `get --key --resolve` and `remember --key` use it, and the other one doesn't show as a layer. After `sync` (and `omoi import <file>`) the other one is marked superseded by it (a `superseded` verdict with the reason "same key … written on two computers"), so the review proposes forgetting it; nothing is deleted. `sync --json` says how many as `duplicate_keys`. A pair that already has a verdict is left alone: after "It's fine as it is" the next sync or import doesn't mark it superseded again. Only a verdict this same rule left the other way round (the one that lost was changed later and now rules) is turned around.

### OKF names with accents on macOS
- macOS (HFS+) keeps file names in NFD (the accent apart from the letter) and lists them that way. `import --okf` now reads concept paths in NFC, so a concept from a bundle that went through a Mac is the same concept (with its signature) and not a new memory, and the mirror export compares names in NFC, so it neither deletes the concept it just wrote nor leaves an old copy named in NFD on a system that doesn't normalize. A title saved in NFD gives the same file name as in NFC (`café-con-leche`, not `cafe-con-leche`). New dependency: `unicode-normalization`.

### A link to a memory
- The web view opens a memory from its link: `http://127.0.0.1:7438/#/memoria/<id>` (the whole id or its beginning, at least 4 characters) shows its project with that memory in the side panel, Verify button included; in a narrow window it scrolls down to the panel. A link to a memory the view doesn't have (forgotten, from another client's space, mistyped) says so instead of showing an empty page.
- `omoi serve --memory <id>` prints that link and, with `--open`, opens the browser on it (also when a server is already running on that port). The id can be its beginning, as in every other command; an id no memory has, or a memory the view started from that folder wouldn't show, is an error before anything starts. With `OMOIKANE_HTTP_TOKEN` the opened address is `#token=<token>&to=/memoria/<id>`, and the page swaps it for `#/memoria/<id>` after keeping the token. Kumi uses the link when an approval went through an agent: it leaves the memory unverified and sends the person a notice with the link, so the person verifies it by hand ([saving.md](docs/saving.md#verified-by-a-person)).
- The project page in a narrow window (under 900 px) no longer overflows sideways: its columns, counters and the memory panel fit the width (checked at 400 px, dark and light).

### Verifications keep counting when the sync keys change
- After `omoi sync rotate`, `sync join`, `sync init` or `sync off` on the general repository, a person's verifications used to stop counting where they arrived through a space repository: the verification key comes from the general repository's key, and the other computer didn't have the new one (or this one no longer had the old one). Now the verification keys this database got from a general repository stay noted in local `meta` (`sello_firma_antes`) and keep checking old verifications; after the change, this computer re-signs with the current key the verifications it holds as the person's own (their signature checks out with one of its keys and they aren't marked as someone else's), so a computer that only has the new key accepts them once the next sync carries them; and the verifications it had marked as someone else's (`sellos_ajenos`) are checked again with the keys it has now, so a computer that receives the new code after another one rotated sees them verified at once. Nothing becomes the person's own without a valid signature.
- After `sync off`, new verifications are signed with the database's own random key, as without a general repository: they count on that computer only. Signing with a remembered key would have needed to know nobody else has it (see the next entry).
- A general repository joined with `--another-person` (a teammate's) no longer gives a verification key: the other person has that key too, so their verifications through a space repository counted as this person's own, and this person's as theirs. Such a computer keeps its database's own key. `join --another-person` now notes it in that repository's `sync.json` (`another_person`).
- A computer that joined a teammate's general repository with `--another-person` in 1.8.5 doesn't have that note, and nothing in its database tells it apart from a computer of the same person (with `--another-person` the configured person was already the local one). Until it joins again, the teammate's verifications keep counting as its own, and `sync off` or a rotation notes that repository's verification key as this person's. On such a computer: run `omoi sync off`, then `omoi sync join <code> --another-person` (joining that way without turning it off first is refused and says so) with a code from that repository. Joining that way forgets the noted verification keys it recognizes as that repository's, and verifications that arrived through a space and no longer check out with the remaining keys stop counting. If that repository's key was rotated while this computer was in it (it can't recognize keys from before the rotation), run `omoi sync forget-seal-keys` between the two: it forgets every noted verification key (only from a person's own terminal, like `omoi verify`), and this person's own verifications signed only with one of them stop counting on this computer until verified again.

### Paths
- A local path with the extended-length prefix (`\\?\C:\…`, what Windows' `canonicalize` gives and some programs use past 260 characters) is local again in `--db`, `OMOIKANE_DB`, `OMOIKANE_HOME`, `OMOIKANE_MODELS`, `--dir` and everywhere else a folder is checked; 1.8.5 refused it as a network path. Only with backslashes, a drive letter and no `..` (with that prefix Windows passes the path on without normalizing it); `\\?\UNC\…`, `\\?\GLOBALROOT\…`, `\\?\Volume{…}`, `\\.\…` and `\??\…` are still refused.
- `project` over MCP (in `remember`, `update`, `search`, `recent`…) is accepted when it is the session's own network working folder (the folder the MCP server runs in, or the `cwd` its agent's hook sent) or that folder's repository root, written any way (`\\?\UNC\…`, forward slashes, another case, a trailing slash): 1.8.5 refused it although that folder is already being read. Any other network path, also another folder of the same share or one inside the working folder, is still refused without touching the disk.

### Secret redaction
- A password written by hand is redacted: a word that names one followed by `:` or `=` (`password: hunter2`, `DB_PASSWORD=…`, `PGPASSWORD=…`, `"password": "…"`, `passwd := '…'`, `pass=…`, `PWD=…`, `--password …`), or in a sentence, in Spanish or English, followed by "is"/"es" ("the wifi password is …", "la contraseña es …", "la contraseña del router es …"). Only the value becomes `[redacted:password]` (a closing typographic quote, `”` or `’`, isn't part of it). To tell it from ordinary prose ("la contraseña se guarda en el llavero", "password reset flow", "the password is required"), the value has to look like a password: 4 to 128 characters with a digit or a symbol, and not a placeholder or code (`$VAR`, `%VAR%`, `<yours>`, `${{ secrets.X }}`, `****`, a path, `os.environ["X"]`, `getpass()`, `config.db_password`, a comparison with `==`). A plain word is missed ("swordfish"): that is the price of not flagging prose. `pass` and `pwd` count only with `=` ("Tests pass: 45/45" isn't one). The 1,836 lines of `tests/corpus.txt` still give no false positive.
- LinkedIn member ids (`ACoAA…`, and `ACwAA…` from Sales Navigator), which LinkedIn puts in its URLs (`?rcm=ACoAA…`, `/in/ACoAA…`), were redacted as tokens. They are a profile's public id, not a secret, and are left alone, as is the value of any `rcm=`. A real token in another parameter of the same URL is still redacted.

### Proposed recipes
- PowerShell cmdlets are recognized by the full list of approved verbs (`Get-Verb`) and count as a whole command: `Invoke-Pester`, `Restart-Service omoikane`, `Install-Module …` or `Compress-Archive …` are the steps `invoke-pester`, `restart-service`, `install-module` and `compress-archive`, and what follows them is an argument, never a subcommand. Before, a cmdlet whose verb was on a short list (`Invoke-`, `Start-`, `Register-`…) was dropped, and one whose verb wasn't (`Install-`, `Publish-`, `Update-`…) became a program with its argument as the subcommand. Those that only look, move files or shape the output (`Get-`, `Select-`, `Where-`, `Set-`, `New-`, `Remove-`, `Copy-`…, `Invoke-WebRequest`, `Start-Process`, `Start-Sleep`) are still left out, like `ls`, `rm` or `curl`. A lowercase name counts as a cmdlet only with an uppercase letter or a common PowerShell verb, so `update-grub`, `docker-compose up` and `pre-commit run` stay programs.
- `sudo -u <user> <command>` is `<command>`: the user was taken for the program (`sudo -u postgres psql` gave `postgres`). The same with sudo's other options that take a value (`-g`, `-C`, `-D`, `-h`, `-p`…), `doas -u`, `runuser -u` and `env -u VAR`/`env -C <folder>`.

### Downloads with time limits
- Downloading the models and updates had no time limit: a network that hung halfway (a proxy that never answers, a WiFi that drops without closing the connection) left `omoi model install`, `omoi upgrade` or the background update waiting forever. Each download now has 30 s to resolve and connect (TLS included) and 60 s to get the answer's headers. A model file can take as long as it needs while data keeps arriving (the meaning model is hundreds of MB, over an hour at 100 KB/s): it fails after 120 s without receiving anything, and the whole body has a safety limit of 24 hours. An update (a few MB) has 10 minutes for the whole body. A hang ends with a clear error that names the host or the file. A model file is still written to `.part` and renamed only when it arrived whole; now the `.part` is deleted when it fails. An update is held in memory and only written once its signature and SHA-256 check out.
- The Claude Code plugin downloads the `omoi` binary with `curl --connect-timeout 30` and gives up on a transfer that moves under 1 KB/s for 60 s, within 290 s (`Invoke-WebRequest -TimeoutSec 290` in the PowerShell fallback), and `SHA256SUMS` within 60 s. It downloads to `<package>.part` and renames it only when it arrived whole, so a hang or a cut never leaves half a package under the real name.

### Light model checked by SHA-256
- The light model (potion-multilingual-128M int8) was installed without checking what was downloaded. Its three files now have fixed SHA-256s, as the meaning model's do, and a file that doesn't match fails that source (its files are deleted) and the next one is tried. The hashes were checked against the files on Hugging Face, the `lfs.oid` its API gives and the `digest` of the GitHub Release; they are the same files as always, so an installed model doesn't change.

### Compatibility
- Same as 1.8.5: the database schema stays at 10, `lector_minimo` doesn't move, and the sync lines and the Obsidian and OKF export formats don't change. Versions 1.0 to 1.8.5 read a 1.8.6 database and sync with it.
- The trade detection fingerprint lives in local `meta` keys (`oficios_detectados:<project>`), and the duplicated trade memories in local `meta` too (`revision_duplicadas_oficio`, `revision_duplicadas_oficio_lanzado`); older versions ignore them. The verdict for a repeated key is an ordinary `superseded` verdict, which older versions already sync and show. An older version still picks the oldest memory of a repeated key in `get --key`, as before.
- What is new lives where older versions already keep or ignore things: the remembered verification keys in a local `meta` key, and `another_person` in the local `sync.json` of a general repository (older versions ignore the field). A re-signed verification is the same `verified` field of the memory's line with a new signature; older versions keep and send it on as before.
- Nothing new is stored by the redaction: it applies, as before, to what is saved or changed from now on (a password saved before shows up in Review with its button to redact it), and `[redacted:password]` is ordinary text for older versions. The recipe steps (`session_steps`) are local: a sequence already recorded with an old step name (`postgres`, `install-module psreadline`) simply stops repeating.
- MCP and JSON only add: `duplicate_of`, `similarity` and `duplicate_hint` when promoting to a trade, `duplicate_keys` in `sync --json`, and the review kind `trade_duplicate`. New flag `omoi serve --memory <id>` and new command `omoi sync forget-seal-keys`. No tool or argument is removed.

## 1.8.5 (2026-11-08)

### Leak check says where
- Each leak in `trade_leaks` now says in which `field` it was found: `title`, `content`, `paths`, `tag`, `key`, `data` or `answer` (the CLI prints it after each one). A key that names a project (`kumi-route` names Kumi) is a common case: knowing it's the key, you rename it instead of rewriting a text that was already clean. Reported by Kumi, the first program using trade keys.
- The docs show the real `scope` of a trade layer in `get --key --resolve`: `trade:web` (several trades joined with commas), not `trade`.

### Code that changed under a memory
- The review flags a memory whose files changed a lot since it was written or last checked: *code changed under them* (`code_drift`), in `omoi review`, in `context`, in the web view's Review tab and in the notice at the start of the session. Its files are its `paths` and the ones it names with their folder (`src/sync.rs`, not a bare `main.rs`) that exist on this computer. It counts as a lot when the lines changed since then (added plus removed, from `git log --numstat`) are at least half of what those files measure today and at least 20; for files outside git, when they were edited in 5 different sessions of the session diary, not counting the one that saved the memory. What changes in the 6 hours after writing it doesn't count: saving the memory and then committing the work it describes is the normal thing. It only proposes a check and never touches the memory; "it's fine as it is" (`omoi review --dismiss <id> --kind code_drift`, or the web view's button) marks it checked, and it comes back only if the files change a lot again after that. A file that is gone is still a broken path (`broken_path`).
- Measured on a copy of Marc's real memory (225 memories; 66 with files that exist, 23 through their `paths`): it flags one, the note saying the outdated-memory detector "still isn't incremental" (56 % of `src/copia.rs` and `src/revisar.rs` changed since; it is incremental now). Counting commits didn't separate: 5 or more flagged 9, mostly touch-ups (7 commits that changed 27 lines out of 535, a catalog regenerated on every release). Behind the one flagged, the history of Omoikane's phases (42 %) and a decision about an experiment (38 %), both still true, and the rest under 22 %. The session diary is a week old there and flagged nothing.
- Never in each prompt's recall. The result is kept per memory (in `meta`, local) and holds while the memory doesn't change, so the full review costs about 1 ms more and the notice at the start of the session only reads what is kept, with no git and no disk. Once a day, if what is kept is from another day, a background process (`omoi review --refresh-drift`, launched by Omoikane) works it out again: the `mtime` of each file first, then one `git log` per repository, only with the files modified since, in parallel; on that memory, 0.6-0.9 s, nearly all of it starting git in 8 repositories. The first time, `omoi review` and the web view work it out; `context`, which an agent calls at the start of a session and waits for, doesn't: it launches the background process and shows it in the next one. Each `git log` gets 10 seconds; past that it is stopped and those files count as outside git.

### OKF bundles: export and import
- `omoi export --okf <folder>` writes the memory as an [OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) bundle, the Open Knowledge Format that okf-agent-memory uses: one Markdown concept with a YAML header per memory in `<group>/<kind>/<title>.md`, an `index.md` in every folder (the root one with `okf_version: "0.2"`), a `log.md` by date and an `overview.md` per project linking to its memories. The kind becomes `type` (`Fact`, `Decision`, `Gotcha`, `Preference`, `Procedure`), title and content go as `title` and the body with its first sentence as `description`, tags as `tags`, paths inside the repository as `code_refs`, `review:YYYY-MM-DD` as `stale_after`, a memory verified by a person as a `verified` entry by `human:<who>` (see below), `draft` and `deprecated` tags as `status`, a superseded memory as `status: deprecated` with a link to the one that replaced it, and the agent that saved it as `generated.by`. Id, key, pin, dates, author, absolute paths and data go in an `omoikane:` key, which OKF tells consumers to keep. Same scope and isolation as `--obsidian`: personal projects and global memories, or `--space <client>` alone without the global ones. It is a mirror: it writes only what changed, deletes only its own files, and refuses a folder that holds someone else's bundle.
- `omoi import --okf <folder>` (also a repository with the bundle in `knowledge/`) checks first that it is OKF (every `.md` other than `index.md` and `log.md` with a readable YAML header and a `type`) and says which files are wrong before writing anything. Each concept becomes a memory in this folder's project (a concept from a project this database also has goes back to it), in a space with `--space`, or in the global memories with `--global`; from the home folder it refuses without one of those, because everything would become global. A concept exported from this same database keeps being global and pinned and comes back with its own id, key, dates and verdicts, to the memory it came from, wherever that is now (a global memory moved into a project after the export is updated there, not duplicated). A concept from any other bundle, also one from another Omoikane database, is someone else's: it goes to the destination you asked for, unpinned, with a new id under the key `okf:<concept path>`, whatever its `omoikane:` key says (its id, key and `project_key` decide nothing; see the verification below). A concept that would become a trade memory (global with `trade:`) goes through the trade leak check, without `allow_leaks`: if it names a project or a client, that concept fails before anything is written. Importing twice changes nothing. Other tools' types map by name (`Runbook` is a procedure, `Convention` a preference, the rest facts); what OKF has and Omoikane doesn't (`sources`, `resource`, `generated`, process verifications, `governance`, the original `type`…) goes into the memory's data under `okf` and comes out again on export. Title, content and data go through secret redaction like any `remember`. A bundle exported from a space only goes into a space (`--space`), and personal memories don't go into a client's project. A memory forgotten here (in the trash or with its forget mark) doesn't come back with its id: it is skipped and counted (`skipped_forgotten`), as sync does with a forget; `omoi restore` brings it back. `--dry-run` says what would be new and what is already there, and how many would come in global, pinned or verified. Symbolic links and Windows junctions inside the bundle aren't followed, a concept (or `index.md`) over 1 MB is skipped with a warning, data over 64 KB fails that concept before creating its memory, and a folder with over 20,000 files and folders, 50 MB of concepts, 16 MB of YAML headers or 2 million values in them, or a concept whose YAML header is over 256 KB, is refused whole, before anything is written. Into a client's space (`--space`), a bundle that would bring pinned or verified memories, or Omoikane memories from outside that space (personal or another client's), is announced and imported only with `--yes` (in a terminal it asks), because that space's repository is shared with other people.
- **How it knows a bundle is its own.** Each exported concept carries `omoikane.sig`, an HMAC-SHA256 with a random key of this database (`meta`, never synced nor in `omoi export`) over everything the import applies from it, read back from the written concept exactly as the import will read it: its path, id, key, `project_key`, scope and pin, kind, title and content, paths, tags (including the ones `status` and `stale_after` become), data, dates, source, `superseded_by` and `contradicts`, and its verification (who, when and `omoikane.verified_sha`, the fingerprint of the verified text). Only a concept whose signature checks out is trusted with `scope: global`, `pinned`, a person's `verified`, its id and key (which memory it updates) and its project. Editing any field of a concept in the Markdown makes it someone else's concept: it can't keep being global or pinned with a new text, nor change the tags, paths, data or verdicts of the memory it came from. A verdict never joins a concept of this database with one without its signature. A concept of this database older than its memory here (its signed `updated` is earlier) leaves that memory untouched (text, verification, verdicts) and is counted in `skipped_older`. The ids existing here wouldn't be enough: anyone who saw one of your bundles has them. A bundle you exported on another of your computers counts as someone else's (each database has its own key); to move a whole database, use `omoi export` and `omoi import`.
- Verification goes through the real mark, never through a tag (agents can set tags). On export, only a memory whose verification still holds (`omoi verify` or the web view, with the text unchanged since) gets `verified: [{by: human:<who>, at}]`, with the date it was verified; a space in the name goes as `%20`, because an OKF actor has none. A `verified` or `verified:<who>` tag is just a tag. On import, which is the person's own action, a person's `verified` entry (`human:<who>`) verifies the memory with its original date only if the concept was exported from this database (its signature checks out) and its text is still the one verified (`verified_sha`): editing the Markdown and importing it again doesn't keep the verification. From someone else's bundle it verifies only with `--trust-verified`. Never when it predates the concept's `generated.at` (OKF counts that one as superseded), when the person unverified that memory here after that date, or when the date is more than a day in the future. Inside a coding agent's shell the memory always comes in unverified (also with `--trust-verified`) and the import says so, to be repeated from the person's own terminal. Verifications by processes (`process:…`, `<producer>/<version>`) never verify anything: they are kept in `data.okf` and come out again on export.
- The YAML of the headers is read without a new dependency: maps and lists by indentation, `[…]` and `{…}` (also across lines), quotes, `|` and `>` blocks; anchors, aliases and tags are refused with the line.
- okf-agent-memory's own `okf validate --strict` (v0.8.0) passes on the export of a copy of the real database (230 memories, 264 concepts, under a second) and on its re-export after importing it into an empty database; importing okf-agent-memory's own `knowledge/` (26 concepts) twice gives 26 new and then 26 unchanged. Its tool wants `stale_after` as a bare date and warns on the datetime the OKF spec asks for (`2026-12-01T00:00:00Z`); Omoikane writes the spec's form and reads both.

### Verified by a person
- A memory can be **verified by a person**, apart from what agents write: `omoi verify <id>` (it shows the memory and asks; `--by <name>`, by default your sync name or the system user; `--unverify` removes it) or the new **Verify** button in the web view. It keeps who and when. The recall marks it `[decision, verified]`; search, `get`, `list --json`, `recent`, `context` and the MCP results carry `verified` (`{by, at}`, or `"by Marc, 2026-11-08"` in compact results), and the web view shows a ✓.
- An agent can't verify anything: there is no MCP tool, `remember` and `update` ignore a `verified` field, the HTTP tools are the MCP ones, `omoi verify` refuses without a terminal unless `--yes` and always refuses inside a coding agent's shell (the variables agents really set when they run a command: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `AI_AGENT`, `AGENT`, `GEMINI_CLI`, `CODEX_SANDBOX`, `CODEX_THREAD_ID`, `CURSOR_AGENT`, `OPENCODE`, `CLINE_ACTIVE`, `COPILOT_AGENT`, `WINDSURF_CASCADE_TERMINAL` and more for Qwen Code, Kilo, Crush, Amp, Goose, Roo, Augment, Junie, Kiro, Trae and Antigravity; not a person's own configuration such as `CLAUDE_CODE_USE_BEDROCK` or `AIDER_*`), and the web button goes through `POST /api/verify`, which wants the view's `Origin` and a token that `omoi serve` generates on each run and puts only inside the page. Imports carry verifications too, never inside an agent's shell: `omoi import --okf` (see above) and `omoi import <file>`, which keeps the verifications this person signed and someone else's only with `--trust-verified`. Sync brings the verifications made on the person's other computers: they travel through the person's own encrypted repository and are that person's trust. Each verification carries an HMAC (of the memory's id, who, when and the text's fingerprint) with the person's verification key, derived from the key of their general (personal) sync repository, so it is the same on all their computers and nobody else has it (without a general repository, a random key of that database). One that arrives through a client's space repository (shared with other people) without that signature doesn't count as verified here, whatever name its `by` says; it stays in the memory, untouched, for the others. None of this is a security boundary against an agent with a shell that sets out to get around it (it can also edit the database or load the page to read the token); it makes sure no normal path of an agent ends in "verified". The agent's instructions say to trust a verified memory over an unverified one that disagrees and never to verify on its own.
- Changing the text (title, content or kind) removes the verification and records when (`unverified_at`, as `--unverify` does), and `update` says so (`unverified`, on stderr and in the JSON) so the agent tells the person. Tags, paths, pinning and moving keep it. The mark carries a fingerprint of the verified text, so a change made by an older version, which keeps the mark without understanding it, leaves the memory unverified too.
- The review puts unverified decisions and gotchas first in each group, and verified memories last.
- Kumi: `kumi.py` verifies what the person approves (`decisions --resolve`, then `verify --by <name> --yes`), never from inside the apprentice's session ([saving.md](docs/saving.md#verified-by-a-person)).

### Provenance
- Each new memory keeps the agent session and the commit it was written in: `provenance: {session, commit, branch}` in the JSON, and a `written in` line in `get` and `history`. The session comes from `OMOIKANE_SESSION`, `CLAUDE_CODE_SESSION_ID` (Claude Code sets it for its shell and its MCP servers) or the only session the hooks registered in that project in the last 12 hours; the commit is the project's HEAD, read from `.git` without running `git` (worktrees and `packed-refs` included). Later changes don't touch it. Trade memories don't carry it (promoting one removes it), and global memories and a space's own memories carry only the session: the commit and branch would be those of the folder they were written from, perhaps a client's (`feature/acme-…`), and those memories are seen from elsewhere. Moving a memory to global drops them too, and `get`, the web view and `omoi export` never show them for a memory without a project.
- Measured in-process (release, 400 interleaved saves, no model): saving goes from 0.97 to 1.32 ms in a normal repository and from 1.20 to 1.71 ms in a worktree (two more files to open). A whole `omoi remember` (release, new process each time, 30 interleaved rounds) doesn't show it: median 563 ms in a repository with a commit against 608 ms in one without, both noise.

### Fixed
- `remember` from the home folder looked up on disk the paths a memory names to find its repository, and `~/` or `~\` followed by `\\host\share`, `//host/share` or `\\?\UNC\…` became a network path once joined to the home folder (`join` keeps the second absolute path): an SMB connection to whatever the memory said, with the person's NTLM hash. Those paths are never looked at now, and neither are network paths in a worktree's `gitdir:`, in the file of `omoi import`, or in folders that come from environment variables (`--db`, `OMOIKANE_DB`, `OMOIKANE_HOME`, `OMOIKANE_MODELS`, `HOME`/`USERPROFILE`, `COPILOT_HOME`, `GROK_HOME`, `XDG_CONFIG_HOME`, `APPDATA`), which are an error.
- `import --okf`: a signed concept copied with its text intact and edited elsewhere could change, in your memory, its tags, paths, data, `status` and `stale_after`, and create `superseded_by`/`contradicts` verdicts towards a concept from someone else. The signature now covers everything the import applies, and verdicts never join a signed concept with an unsigned one.
- `import --okf`: an old bundle of this database put a memory back to its old text and verified it again with the old date. A concept older than the memory here leaves it alone, and the verification comes back only if `verified_sha` matches the memory's text as it is after the import.
- Sync: whether a verification arriving through a space repository was the person's own was decided by comparing its `by` with the local author, and anyone in that space can write any `by`. It is decided now by the HMAC with the person's verification key (see above).
- `remember` over MCP with `supersedes`/`contradicts` saved the memory first and then failed on a memory of another space, with an error that gave that memory's whole id and the other space's name. The ids are now checked as `update` does, before saving, and no error names ids or spaces from elsewhere (also the out-of-scope errors of `get`, `update`, `history` and `forget`).
- `import --okf`: 192 MB of `[…]` headers of 1 MB each took 60 s and 7.5 GB of RAM. Headers are now capped (see above) and measured before they are parsed.
- `omoi import <file>` trusted any verification in the file; it now follows the same rule as `import --okf` (the person's own, or `--trust-verified`; never in an agent's shell).
- Paths that aren't on this computer are never looked at: a memory's path or a file it names that starts with two slashes (`\\server\share\a.py`, `//cdn.example.com/x.js`, `\\?\…`, `\\.\…`) is no longer taken as a file by the code-drift check, the broken-path check (`broken_path`, older than this release) or the session diary's path resolution. On Windows, just checking whether such a path exists opens an SMB connection: it could hang the review and hand the person's NTLM hash to whatever server the memory named.
- The trade leak check says the `field` where a leak appears as a whole word (a space named «QA» is in the content that says "QA", not in a title that says "Qatar").
- `import --okf`: a concept without this database's signature that carried the `omoikane.id` of a memory here rewrote that memory wherever it was (a pinned global one, another project's, a trade memory) and skipped the leak check; its `project_key` could send it to another project than the one asked for. Now such a concept never matches by id, key or project (see above), the signature covers the text too, and trade memories created or changed by an import go through the leak check. The import's message no longer says the concepts "go to <destination>" when they didn't.
- A memory id given in lowercase (ULIDs accept it) is the same id everywhere: an OKF concept with the lowercase id of a forgotten memory brought it back, and one with the id of a live memory failed with `Query returned no rows`. In the web view, `POST /api/review/dismiss` with a lowercase id or just its beginning got past the space check (it looked for the id as given, found nothing and let it through) and recorded the verdict on another client's memory; it now resolves the ids first. The MCP tools (`get`, `update`, `forget`, `history`…) already resolved them; sync and `omoi import <file>` refuse any id that isn't canonical.
- No network path is ever opened, also when it comes from outside: a `project` given over MCP, `?dir=` in the web view (which any web page can request with an `<img>`), `--dir`, the folders of `export`/`import --okf` and `--obsidian`, a project path that arrives by sync or in an engram export, and the transcript path of a hook. `\\host\share`, `//host/x`, `\\?\UNC\…`, `\\.\…` and `\??\UNC\…` (which Windows passes through as an NT path) are refused before touching the disk; before, each one opened an SMB connection, took about 21 s to fail against an unreachable host, blocked the web server meanwhile and handed the person's NTLM hash to that host. The folder you work in can still be a network share (see the next entry).
- Working in a network folder (a shared drive `\\server\share\…`, `\\wsl$\…`, `\\wsl.localhost\…`) broke with the fixes above: Omoikane no longer read the repository there, so a new project got `dir:<person>/<name>` instead of its `git:github.com/…` key (from `\\localhost\D$\…`, `dir:…/netrepo` where 1.8.0 gave `git:github.com/acme/netrepo`), its folder never counted as seen (`last_seen`), new memories had no commit in their provenance, and the hooks failed when the agent's `cwd` was such a folder. The folder you work in is trusted again, also when it is on the network: the folder `omoi` or the MCP server runs in, and the `cwd` the agent's own hook sends (its session's folder). There the repository is read as in 1.8.0 (`origin`, `HEAD`, the common git folder of worktrees, whether it exists), anywhere in that same share (`\\server\share`), since the system is already connected to it. Everything that comes from outside (a memory's text and `paths`, `project`/`dir` over MCP, `?dir=`, `--dir`, sync, bundles, environment variables) still goes through the local-path check, and another share of the same server counts as outside. WSL paths count as local everywhere when WSL serves them (its P9NP network provider ahead of the SMB client): they reach WSL's virtual machine on this computer, not another machine over SMB. Without WSL those names would be looked up on the network, so they stay refused.
- Changing the text of a verified memory removed its verification without recording when, as `verify --unverify` does (`extra.unverified_at`). A newer line carrying the old text and its old verification (another of the person's computers that hadn't seen the change yet, an `omoi import <file>`) made it verified again, since with the old text the fingerprint matched. The date is recorded now, kept when a newer line arrives, and a verification older than it no longer comes back through sync or `import <file>` (through a space repository it stays in the line for the others and doesn't count here, as before; `import --okf` already checked the date).
- `import --okf`: a bundle that git checked out with `\r\n` (`core.autocrlf=true`, the Git for Windows default) no longer passed as this database's own: each concept came in again as a new memory, duplicated and without its verification. A concept whose header starts with `---\r\n` is read back with `\n`, as it was written and signed.
- Reading an OKF header with a `[…]` spread over many lines was quadratic (400 KB took 15 s): it is linear now. `index.md` has the same limits as a concept.
- The code-drift check's `git log` stops at its time limit even when `git` leaves a child holding its output (Git for Windows' launcher does): it waited for that child, 15 s with a 0.5 s limit.
- `omoi serve` compares its tokens (`OMOIKANE_HTTP_TOKEN` and the view's) in constant time.
- Sync: a verification that arrived inside a trash line (`forgotten`) through a space repository counted as yours once you restored it (`omoi restore`), whoever wrote it. It now follows the same rule as a `memory` line: without your signature it is someone else's and doesn't count here.

### Compatibility
- Same as 1.8.0: the database schema stays at 10, `lector_minimo` doesn't move, and the sync lines and the Obsidian export format don't change. Versions 1.0 to 1.8 read a 1.8.5 database and sync with it.
- What is new lives where older versions already keep things they don't understand and send them on unchanged: the verification, when the person last unverified it and the provenance in `memory.extra` under their own keys (`verified`, `unverified_at`, `provenance`), as fields of the memory's line, also after editing the memory (`tests/compat.rs` checks it against 1.0.0); a concept's extra OKF fields in the memory's data (`data.okf`); "it's fine as it is" for `code_drift` as an ordinary `ok:code_drift` verdict; and the worked-out drift and the OKF signing key in local `meta` keys. Older versions just don't show them, and a text change made there leaves the memory unverified when this version reads it.
- MCP and JSON only add: `field` in each `trade_leaks` entry, `verified` in compact results, `verified` and `provenance` in `get` and the full results, `unverified` in `update`, `unverified` in the `file` counts of `import <file> --json`, `sellos_ajenos` in `sync --json`, and in `import --okf --json` `verified`, `not_verified`, `untrusted_verified`, `stale_verified`, `global`, `pinned`, `foreign`, `ignored_global`, `ignored_pinned` and `skipped_forgotten`; no tool or argument is removed. `GET /api/memories` carries both fields, and there is a new `POST /api/verify` for the web view (it needs the `X-Omoikane-View` header with the token inside the page, which the page sends). Clients that don't know these fields can ignore them.
- Paths: a network path in `--dir`, `project` (MCP), `?dir=` or an export/import folder is now an error instead of being opened; map the share to a drive letter, which keeps working. Working from a network folder works as in 1.8.0, and `\\wsl$\…`/`\\wsl.localhost\…` are accepted everywhere when WSL is installed. More environment variables make `omoi verify` refuse (see above): a script that ran it from inside an agent's shell with only some of them unset now has to unset those too (`omoikane::verificado::DE_AGENTE` lists them).
- New flags `import --okf --global`, `import --okf --space … --yes` and `--trust-verified` (also for `import <file>`). `import <file>` into another database (another person, or a computer without the person's general sync repository) now leaves out the verifications that person didn't sign unless `--trust-verified`. A verification arriving through a space repository counts as the person's own only with their signature: on a computer that only joined the space (not the person's general repository), the person's verifications from other computers don't count. `import --okf --space` with pinned, verified or out-of-space memories needs `--yes` without a terminal. A network path in `--db`, `OMOIKANE_DB`, `OMOIKANE_HOME` or `OMOIKANE_MODELS` is now an error. New counts `skipped_older` in `import --okf --json` and `untrusted_verified` in the `file` counts of `import <file> --json`. The OKF signature changed (`omoikane-okf-3`): bundles exported by earlier 1.8.5 builds count as someone else's; export them again. `import --okf` run from the home folder without `--global`, `--space` or a project's `--dir` now refuses instead of making everything global. Exported concepts carry two more keys under `omoikane:` (`sig`, `verified_sha`), which other OKF tools keep without understanding.

## 1.8.0 (2026-11-07)

### Trades: memory for each stack
- A new level between the project and the global memories: the **trade** (android, web, wordpress, rust, python…). What one stack teaches ("don't kill the Android emulator with `taskkill`") is saved once with `remember --trade android` (`trade: "android"` over MCP) and reaches every project of that trade, of any client, and no other: a client's web project never gets the Android trap. In search, recall, `recent`, `context`, the web view and `get` by id. From the home folder, all of them. `update` with `trade` turns a memory into a trade memory, and `trade: ""` turns it into an ordinary global memory (it doesn't go back to the project it came from); moving it to a project or a space drops the trade.
- Each project's trades come from its files: the root and one level of subfolders, never the whole tree (Gradle with Android, `AndroidManifest.xml`, `astro.config.*`, `next.config.*`, a `package.json` with a web framework, `wp-config.php`, a theme's `style.css`, `Cargo.toml`, `pyproject.toml`, `.claude-plugin/`, Electron or Tauri, `skill-package/`… 27 trades, several per project, all listed). The names are those of Kumi's production lines (`android`, `web`, `rust`, `plugin-claude`, `python`, `escritorio-node`, `alexa`); `seo-geo` can't be told from the files and is set by hand. They're worked out at the start of each session, in `context` and the first time a project is used, and only written when they change. On Marc's 33 real projects it found what each one is (Android apps, Astro webs, Rust tools, Claude Code plugins, Python tools, an Alexa skill), with nothing for the two that are only Markdown.
- `omoi trades` shows a project's trades and where they come from; `add`, `remove`, `set` and `auto` correct them; `list --all` shows every project's and how many trade memories each trade has. `omoi projects`, `context` and `/api/projects` show them too, and the session start tells the agent the project's trades and when a trap belongs to the trade.
- A trade memory reaches every client, so before saving one Omoikane looks for what belongs to someone: a project's name, a space's (a client), an absolute path of yours, the URL of one of your repositories (or any SSH one), a client's git server, or a domain that only shows up in a client's memories. It looks at everything the memory carries: title, content, paths, tags (except the reserved ones: `trade:`, `trade-for:`, `review:`, `open`, `blocking`, `resolved`, `status`), the key and the data (its keys and texts), comparing names without case or accents ("balua" is Balùa) and space names from 2 letters. If it finds any, nothing is saved and the agent gets `trade_leaks` with what it found (exit code 2 in the terminal), to rewrite it or save it in the project. `update` checks what's new in a trade memory (its tags and data too, even when that is all it changes), and everything when a memory becomes one; resolving a trade decision checks the answer. `force` only skips the duplicate check, as before: agents send it routinely, so it no longer lets leaks through. For a false positive someone has looked at (a library named like a project) there is `allow_leaks` (`--allow-leaks`), which never lets through an absolute path or a repository URL.
- Any kind can be a trade memory. Trade preferences and pinned ones are injected at the start of every session of a project of that trade, next to the global preferences ("new screens go in a `Scaffold` and use its padding" reaches the next Android app from its first session); the rest come with recall.
- `--for client|personal` (`for` over MCP) keeps a trade memory for the projects in a space (a client's) or in none (yours); both by default. "Review the landing's SEO and GEO" as a `web` preference `--for client` reaches every client's web and not a personal one. Nothing new on the project: the space says it. In session start, recall, search, `get` and the web view.
- `omoi update <id> --trade android` (`update` with `trade`) promotes a memory of a project to its trade, after checking all it will carry (a client's has to be rewritten in that same update). A personal memory (a project in no space, or a global one) moves with the same id, history and verdicts. A client's memory (in a space, or in one of its projects) doesn't move: a **new** trade memory is created with the rewritten text, a new id and no history or verdicts (`promoted_from` in the answer), and the client's memory stays where it was, with its history, travelling through the client's repository. Moving it took the client's history and verdicts to every client and left a copy on the client's other computers that sync then refused. Forget the original if it only repeats the new one.
- Nothing of a client leaks through what is shown next to a trade memory either: `history` (MCP, `omoi history`, the web view) and `omoi export` never return versions of a memory outside the scope; the notes on a memory in `search` and in the recall ("superseded by…", "contradicts…", "may be outdated…") only name the other memory, its title and the reason if it can be seen from there (otherwise "superseded by a newer memory that is not in this scope"); nor do the hints of `remember` about memories it makes outdated. `update` with `absorb` refuses to merge a client's memory into a global or trade memory (it would carry its history, tags and paths to every client).
- Sync: trade memories go only through the general repository (with global sharing on, like global memories), never through a client's, and a client's repository can't bring one in (the line is refused).
- Measured on a copy of the real database plus 20 trade memories (233), release, whole process, 30 interleaved rounds against the published 1.7.2: a prompt's recall P50 129 ms against 150 from a project with trades and 123 against 142 from the home folder; the session start (which now looks at the project's files) 111 against 145 and 128 against 135. The machine was busy and the noise is large: what it says is that it costs no more. Hidden trade memories go through a partial index, read once per query. Of the 134 real global memories, 71 would be refused as trade memories, all for naming Marc's projects or his paths: none of them is stack knowledge.

### Added
- **Blocking decisions.** An open decision (kind `decision`, tag `open`) can also carry the tag `blocking`: work that depends on it can't go on without the user's answer. Without it, it is for later, as before. The session start lists the blocking ones first and marked `BLOCKING`, and the agent's instructions say when a decision is blocking (no safe assumption, or a wrong guess would be costly to undo) and that it should stop that part and ask. In the web view, **Projects** and **Overview** show which are blocking (Overview counts them), and answering one drops both tags.
- `omoi decisions` (with `--blocking`, `--project`, `--space`, `--all` and `--json`) and the MCP tool `decisions` list the open decisions with their `priority` (`blocking` or `later`), blocking first, for programs that hand out work, such as an agent factory's dispatcher. They respect spaces like `recent`: from a client's project, never another client's. `--tag` narrows them to those with other tags too (`tarea:42`).
- **Resolved decisions.** `omoi decisions --resolve <id> --answer "…"` (and `resolve` with `answer` in the tool) appends the answer, drops `open` and `blocking` and adds `resolved`, keeping the previous version. The web view's **Decide** adds `resolved` too. A decision that is already resolved isn't resolved again (an error that says to `update` it), and the answer to a trade decision goes through the leak check (`allow_leaks` / `--allow-leaks` as in `update`). The web view now says why when a save is refused for leaks, instead of failing silently. Open-blocking, open-for-later and resolved are all tags, so the text no longer needs markers like `[blocking]`.
- `omoi list --tag <tag> [--tag …] [--kind …] --json`: every memory with those tags in the scope, newest first, with no search, ranking or threshold, for programs that save something under a tag and must always find it again (`search` could rank it out). Agents get the same with `recent` and `tags`.
- **Data for programs.** A memory can carry any JSON up to 64 KB, apart from its text: `--data '<json>'` in `remember` and `update` (`--no-data` removes it), `data` in the tools (`null` removes it), returned by `get`, `list --json`, `decisions --json` and `recent` with `tags`. It is never searched or recalled; what looks like a secret in it is redacted; changing only the data adds no version.
- `omoi file-history <files…> --json` gives the session diary's history of some files to code, such as a risk gate that reads a diff: per file, in how many sessions it changed, the last day, up to 10 files that changed in the same sessions (with how many) and the gotchas whose paths name it (count and ids). It takes paths relative to the repository or absolute, or reads them from standard input (`git diff --name-only | omoi file-history --json`), for the project of the current folder or `--dir`, and also counts sessions opened in another folder (such as the home folder) that edited files of the repository. It only reads, and has no thresholds.

### Project names that tolerate typos, and duplicated projects
- A project name is compared ignoring case, accents, hyphens, underscores, spaces and dots wherever one is written (`project`, `--project`, `omoi projects`): `cronicas` finds `Crónicas` and `Social Publish` finds `social-publish`. If nothing else fits, one letter off (changed, extra or missing, from 6 letters) is enough: `Omoikae` finds `Omoikane`. The 1.7.2 rule stays: a name written exactly as one project picks it, and a name that fits several still asks which.
- The review proposes merging duplicated projects, and never merges by itself: the same normalized name; one letter apart only with another sign (one folder gone, the newer one with hardly any memories, or the same git origin); a gone folder that a newer project mentions (`Narrador` → `Aloud`); and "projects" in temporary or upload folders (`.claude\uploads\<uuid>`, `%TEMP%`), to make their memories global or move them to their project. A look-alike name alone doesn't count (`Tokimichi` and `tokimichi-web`). The agent gets it at session start once a day, with `omoi projects merge A B` already written, to ask the user; it also shows in `omoi review`, in `context` (`projects_review`), in the web view's Review tab and in `GET /api/projects` (`duplicates`). `omoi projects distinct A [B]` says they are different (or that a temporary-looking folder is a real project) and it stops coming up.
- Recall understands a misheard project name in a prompt ("onmoikane" for Omoikane, "tokimicho" for Tokimichi): a word that is in no memory and is one letter from the name of exactly one project with memories is searched as that name. Only when both have at least 6 letters, the word isn't the name with an ordinary ending (-s, -ar, -er, -ir, -an, -en, -ed: "faltas" is not Faltis) and the project can be seen from the session (from a client's project, only that client's projects; never another client's). With the first rule, 5 letters, ordinary words became projects in every prompt: on `tests/recall_casos.tsv` plus 8 new negative prompts, the old rule swapped 15 words, 8 of them wrong ("tropa" and "trobar" for Troba, "rodeo" and "rodes" for Rodet, "balsa" for Balùa, "faltas" for Faltis), and one of those injected a wrong memory; the new one swaps 6 (the right ones, plus "kawaneco" in a question about a cat breed, which injects nothing, as before) and loses one right guess ("gruda" for Gruta, 5 letters). Hits: 51 of 69 both ways.
- From a client's project, a project name in `project` / `--project` only matches that space's projects, and the "no project matches" error only lists those.
- Two worktrees of a git repository without an `origin`, in folders with different names, were two projects. They are now one: a new folder joins the project of any folder that shares its git common directory, and a new worktree's key carries the repository's name (`dir:<person>/<repository>`) instead of its folder's. For the same reason, a git folder without an `origin` written two ways (its short Windows name, `CLAUDE~1`, and the long one) is one project, not a second one with a `~2` key.

### Review dates and key-based memories
- A review date per memory, for what stops holding on a known day (a token that expires, an offer, a plan with a date): the tag `review:YYYY-MM-DD` (`omoi remember … --tag review:2026-11-25`, or in `tags` from the MCP). That day the review flags it as *review date reached* (`review_date`) in Review, in `search` and in the recall, and the notice at the start of the session comes even for a single one. Touching the memory or "it's fine as it is" clears it; a new `review:` tag that isn't a date is refused (one that arrives malformed through sync doesn't stop `update`, `--key` or `--resolve`). No schema or sync change: it is a tag. Checked first on a real memory of 213: 7 memories with a known expiry in the next 3 months that the existing review would have flagged 4 to 6 months late.
- A key for "the one memory about X": `omoi remember … --key <key>` (and `key` in the MCP `remember`) creates or updates the single memory with that key at its level, with no duplicate check, and atomically: several processes saving the same key at once leave one memory (tested with 24 writes from 8 processes at a time, CLI and `omoi tool`). `omoi get --key <key>` (and `get` with `key`) reads it. A key lives at four levels, one memory each: project, space (`--space`), trade (`--trade <trade>`, and `--for client|personal` if it is only for one kind of project; each trade and `for` is its own level, and only the projects of that trade see it) and global (`--global`); `omoi get --key <key> --resolve --json` (and `get` with `resolve`) returns every layer the project sees, most specific first, each with its `scope` (`project`, `space`, `trade:<trade>`, `global`), its text and its `data`, unmerged. `--data '<JSON>'` (and `data` in the MCP) goes with it like with any memory (see **Data for programs**): kept out of search and recall, in the same transaction as the key, and changing only the data creates no version; saving the same text and data again changes nothing, and saving the key without `--data` keeps the data it had. With data and no content, the content is the title. The key is a `topic:<key>` tag; a new key that looks like an existing one gets a warning. Two computers that create the same key before syncing do end up with two memories with that key at one level: the key reads the older one (by creation date) and the other stays, until merged with `absorb`. A `preference` is global unless told otherwise, also with a key: `omoi remember -k preference --key x` from a project saves the global `x`. Asked for by Kumi, which keeps one profile per project and got duplicates with two factories in the same repository; on Marc's own memory (86 memories saved with `remember`) no duplicate had slipped past the existing detection, so plain `remember` keeps working as before.

## 1.6.0 (2026-11-06)

### Open decisions
- When the agent runs into a product or business decision that is the user's to make and can't ask right then, it saves it as a `decision` memory tagged `open` (the question, the options and what it assumed meanwhile) and keeps working. The instructions for the agent (MCP, session start and `/omoikane`) say so, and ask it to tell the user which ones it left when it finishes a long piece of work.
- Every session starts with the open decisions of the project, its space and the global ones (from the home folder, which is not a project, those of every project), newest first, one line each with a short excerpt (up to 10, and how many more there are), until the user decides: then the agent `update`s the memory with the answer and drops the `open` tag. They don't count as injected, so recall can still bring them in full.
- In `omoi serve`, the projects page lists the open decisions above the projects; writing the answer and pressing Decide appends it to the memory (with the date) and drops the `open` tag. `omoi search … --tag open` already finds them from the terminal.

### File history
- When a prompt names a file that shows up in the project's session diary (the whole path, or the file name if it has at least 5 characters, as with the gotchas found by path), the recall of that prompt adds one line about it: in how many sessions it changed and when last, which files usually change together with it, and how many gotchas mention it. For example: ``History of `src/recall.rs`: changed in 30 sessions (last 2026-11-04); it usually changes together with `src/main.rs` (18 of 30), `Cargo.toml` (12) and `src/mcp.rs` (12).`` It comes from this computer's sessions, not from a model's guess, so the agent knows how much a file moves before touching it.
- Only for files changed in at least 3 sessions. A file counts as changing together when it shares at least 3 of those sessions and at least 40 % of them; at most 3 are named, and at most 2 files per prompt. When only the name is given and several files share it, the one that changed most. Each file once per session (again after compacting), noted in a new local table, `diary_hint`, kept 7 days: it doesn't count as a recalled memory.
- Most prompts name no file, and that is decided from the text alone, without reading the database: those prompts cost nothing more. Names without an extension (`Makefile`) count only with a folder in front. Measured against 1.5.0, interleaved, on a copy of a real database with a year-sized diary (3,766 sessions, 1.7 MB of file lists): the recall of a prompt that names no file doesn't change (P50 38.5 against 40.2 ms, and 44.3 against 46.4 in a second pass), and one that names a file takes about 5 ms more (44.5 against 40.1, and 49.2 against 43.9).

### Recall from your docs
- A project that already keeps its documentation in Markdown (a `docs/` folder, an LLM wiki, an Obsidian vault) can tell Omoikane where it is: `omoi docs add <folder>` indexes it at once, `omoi docs list` shows the folders with how many files and sections are indexed, `omoi docs remove <folder>` drops one, `omoi docs refresh` brings the index up to date now and `omoi docs test "<prompt>"` shows what recall would bring for that prompt. The folders belong to the project you run it from (or the one given with `--dir`, which a relative folder is also taken from). A drive root or the home folder is refused: it would index everything in it.
- From then on, next to the memories, recall can bring the section of that documentation that fits the prompt: one at most, with its file (relative to the project) and its heading, about 700 characters, each section once per session. It comes marked as quoted from the files, data and not instructions. It is not copied into memory and the files are never written. The rule is the one memories follow (useful words, two rare ones, a share of the prompt's weight), with the bar a little higher (60 % instead of 50 %) because a section is longer than a memory. With Omoikane's own docs and 785 more Markdown files (14,548 sections), on 302 real prompts it brought something once (a borderline case); on hand-written prompts about the docs it brought the right section, and on four that weren't about them, nothing.
- The index splits each `.md` or `.markdown` file by its `#`, `##` and `###` headings (not inside code blocks; Obsidian's YAML header left out) into sections of at most 2,000 characters, in an FTS5 table with the same tokenizer as the memories. Hidden folders (`.git`, `.obsidian`), `node_modules`, `target`, `vendor` and `__pycache__` are skipped, and so are files over 2 MB and anything that isn't a regular file: symbolic links, to files or folders, aren't followed. It is brought up to date when a session starts, reading only the files whose date or size changed and dropping those that are gone, in a separate `omoi docs refresh` that the session start launches and doesn't wait for (at most once a minute per project, like the sync pull, and not while the previous one is still running); until it ends, recall uses the index as it was. An error never stops the session from starting.
- Measured against 1.5.0, interleaved, on a copy of a real database (about 200 memories): the recall of each prompt without docs doesn't change (P50 39.6 against 39.0 ms, noise; the machine was busy); with the 12 files of Omoikane's docs, +0.6 ms; with 797 files, +2.6 ms. The session start no longer walks the folders itself: with 797 files and all of them to index again, it took a P50 of 54 ms against 44 ms for 1.5.0 without docs, and the refresh it launched on the side had the index up to date 1.7 s later. Doing it inside the start, as first written, took about 0.9 s in that case. `omoi docs add` with 785 files took 3 to 7 s.

### Subagent names
- The Claude Code plugin now has subagents named "Project: task" (`Billing app: review login`, `Docs site: fix broken links`), so with several sessions open you can tell which one each agent belongs to. It was the separate `agent-names` plugin; it comes with Omoikane now. The rule goes in the description of the `Agent` tool, and a name that doesn't fit, or runs over 60 characters, is refused with the rule so the model tries again. It only checks the shape, and if the check itself fails the subagent still starts. The `agent-names` plugin is retired from the drac marketplace; if you had it installed, uninstall it (`claude plugin uninstall agent-names@drac`): with both, the model reads the rule twice.

### Compatibility
- Same as 1.5.0: the database schema (10), the sync lines and the export format don't change; `open` is a tag like any other, so older versions sync and show these memories as plain decisions.
- `diary_hint`, kept by the file history, is a new local table created with the first line given, like `diary`, which older versions ignore.
- The docs live in four new local tables (`docs_folder`, `docs_file`, `docs_fts`, `docs_seen`), created by the first `omoi docs add` and not when the database opens, which 1.0 ignores; they aren't synced or exported (the documentation has its own repository and the paths are this computer's).

## 1.5.0 (2026-11-05)

### Proposed recipes
- When a session ends, Omoikane notes the steps that worked (program and subcommand, like `cargo test` or `git tag`; read from the conversation of any of the agents it already reads, leaving out what only looks around, such as `git status` or `git log`, and, in Claude Code, what failed) in a new local table, `session_steps`, kept 90 days. When a sequence of 3 to 6 steps with at least two different programs has come up in 5 sessions, no saved recipe names all its steps and it wasn't proposed before, it is set aside (kind `recipe`) for the next session, and the agent asks the user whether to save it as a recipe. Only sequences of the session that is ending are considered, counted over the 500 most recent sessions (on a synthetic worst case of 1,000 sessions of 300 steps, the whole proposal took 127 ms; with 500, about half), so the cost doesn't grow with the history and the proposal lands in the project where it happens. One each time a session ends or compacts at most, each sequence once. From the web view, saving one creates a recipe with the numbered steps; its `when:` line is left for the user to write.
- Replaying 115 real sessions in order, it would have proposed two: `git fetch → gh issue → gh pr` and `git fetch → git tag → gh release`, in under 1 ms at each session end. Without leaving out the looking-around steps and asking for two programs, the top ones were `git add → git commit → git push`, which everybody does. The conversation is read once for the proposals and the steps: ending the largest real session takes at most 46 ms more than in 1.4.1 (681 against 635 ms, measured before the proposal got cheaper).
- The other idea planned with it, recall from other projects of the same space as a last resort, stays out: on 168 real prompts written inside a project with nothing recalled, only one would have got a memory from another project, and it was noise.

### Fixed
- On Windows the plugin couldn't install `omoi` on networks where `curl.exe` can't check whether GitHub's certificate was revoked, which is common behind company proxies (`CRYPT_E_NO_REVOCATION_CHECK`): the download failed and Omoikane didn't start, after installing and after every plugin update. It now tries again with `--ssl-revoke-best-effort`, which still checks but doesn't block when the check can't be done, and last with PowerShell. The SHA-256 is still checked.
- `omoi`'s own downloads (the model and its updates) now trust the system's certificate store on Windows, macOS and Linux, not only the Mozilla list built into the binary. Behind a company proxy that inspects HTTPS with its own root certificate (installed in the system, which is why Git and PowerShell work there), they failed on every system. ## 1.4.0 (2026-11-04)

Always up to date: what other computers save arrives in the middle of a session, what subagents find isn't lost, the memory says when it needs a look, and each session leaves one line in a local diary.

### Subagents
- When a Claude Code session ends or compacts, Omoikane also reads its subagents' conversations (`<session>/subagents/`) and sets aside, for the next session, the final report of each one that finished (its first 700 characters), with what it was asked to do. A subagent still working, one with something that looks like a secret, and one whose report a saved memory already covers are skipped; at most the 5 newest each time the session ends or compacts. Only the start and the end of each conversation are read: some are over 50 MB. The other signal considered, a command that fails and then works, didn't show up once in 142 real subagent conversations, so it isn't used.
- Measured against 1.3.2, interleaved: the recall of each prompt (P50 29.0 against 28.4 ms) and the start of a session (22.8 against 22.3 ms) don't change. Ending the largest real session (a 73 MB conversation with 74 subagents), with the diary and the subagents, takes 590 ms against 374 ms, within the hook's 1.2 s.

### Sync
- What other computers push now arrives in the middle of a session, not only when one starts. With each message, at most every 2 minutes, `omoi recall` starts `omoi sync --pull` on the side and doesn't wait for it: a `git fetch` and a comparison when there is nothing new, a full sync only when there is. Several sessions at once start one pull between them (the time of the last one is kept in the local `meta` table), and it never runs alongside another sync. `omoi serve` does the same on a 2-minute timer. On most messages it costs one `meta` read, too little to measure; starting the pull adds about 8-10 ms (P50) once every 2 minutes. Without sync set up nothing runs. `OMOIKANE_SYNC_EVERY` (seconds) changes the interval; `OMOIKANE_SYNC_AUTO=0` turns it off with the rest of the automatic sync.
- A pull that fails for a reason that doesn't fix itself (the repository asks for a newer version, a conflict) isn't retried every 2 minutes: only when the remote moves, when something new here is waiting to go up, or after half an hour.

### Session diary
- **One line per session**, written when the session ends or compacts (`omoi recall --session-end`, which already reads the conversation): when it started and ended, the project, the files edited or written (Edit, Write, MultiEdit and NotebookEdit in Claude Code, and the equivalents in Codex, Gemini CLI, Qwen Code, Copilot CLI, Cursor and Grok Build; relative to the repository, up to 50), the memories recall brought into it and the ones saved or changed in it, counting what its Claude Code subagents did (the 10 newest, up to 16 MB each and 32 MB in all). Not the conversation. It answers "what did I do on Tuesday in X?" or "when did we last touch `sync.rs`?", which the `status` memory can't, since it only keeps the latest picture.
- **Saved means its id came back from `remember` or `update` in that conversation**, and the memory still exists. A time window would claim what another session in the same project saved meanwhile. Preferences and pinned memories don't count as recalled: they reach every session.
- **`omoi diary`** reads it, newest first, with `--since` (a date or `7d`), `--until`, `--file <part of a path>`, `--project`, `--space`, `--all` and `--json`. The agent gets the same through `recent` with `sessions: true` (and `since`, `until`, `file`): optional parameters of an existing tool, still 8 tools.
- **Measured on 60 real Claude Code conversations**: 142 bytes per session at the median, 716 on average, 4.6 KB at most. Interleaved over 25 rounds, the diary adds no measurable time to `omoi recall --session-end` on a 1.4 MB conversation (median difference −0.4 ms, noise) and 97 ms on a 73 MB one (577 → 676 ms, within the hook's 1.2 s) (it reads the file once more; only the lines that call a file-writing tool or Omoikane are parsed). Reading its 10 newest subagents (15.8 MB) adds 22 ms more (diary write alone, median of 12 interleaved rounds: 89 → 111 ms). Nothing is added to the recall of each prompt: the table isn't even created when the database opens.
- **Local, kept for a year.** The file paths say a lot about what you do and the history belongs to each computer, so the diary is neither synced nor in `omoi export`; it is in the daily backup, which copies the whole database. At this size a year is about 2 MB at ten sessions a day; older lines are deleted when a new one is written.

### Maintenance that speaks up
- When the review piles up (20 pending items, or 10% of the memories in scope if that is more), the session starts with a three-line notice for the agent: how many there are of each kind and an instruction to look at them with `omoi review` and propose concrete actions (update, `absorb`, `forget`, `supersedes`/`compatible`, fix the links), never acting without the user's OK. Omoikane still carries no language model: the agent decides with the user. It shows once a day per database, and again the same day only if the number grows by at least 5 (or 10%). Agents without session hooks get the same text as `review_notice` in the `context` tool.
- The count at session start reads the cached review, the verdicts and the small columns of each memory, not its contents or the disk, and is cached per day until something is written. Broken paths and possible secrets stay in the full review. On the real 178-memory database the start is as fast as before (P50 22.8 ms against 22.2 ms).

- The database schema stays at 10 and `lector_minimo` doesn't change: the diary is a new local table (`diary`), created with the first line, which 1.0 ignores. The sync lines and the export format don't change.
- The notice and the mid-session pull keep their state in the local `meta` table (`revision_aviso`, `revision_aviso_cifras`, `sync_traido`, `sync_intentado`, `sync_pendiente_intentado`), which doesn't travel.

## 1.3.0 (2026-11-02)

Fast and light again, and still understanding what you ask with other words. 1.2 brought the meaning model to every install and asked it on most prompts; a review in five parts (speed, when to use it, weight, real value, GPU) showed it paid off only with large memories and cost too much in speed and weight. 1.3 keeps the quality and takes the cost back.

### Measured
On the public benchmark ([omoikane-bench](https://github.com/marcmayol/omoikane-bench), 250 questions written blind), interleaved, with 3,000 / 10,000 memories:

| | 1.3 | 1.2 | 1.3 with the meaning model off | engram 3.6 (best mode) |
|---|---|---|---|---|
| recall, P50 | **32 / 54 ms** | 99 / 126 ms | 27 / 31 ms | – |
| search, P50 | **64 / 64 ms** | 101 / 126 ms | 31 / 34 ms | 236 / 347 ms |
| right memory first, paraphrases (search) | 55 % / 53 % | 55 % / 53 % | 9 % / 8 % | 6 % / 4 % |
| right memory first, questions (search) | 89 % / 88 % | 89 % / 88 % | 85 % / 84 % | 71 % / 71 % |
| recall injects something on a question with no answer | 7.5 % / 15 % | 7.5 % / 15 % | 40 % / 70 % | – |
| recall brings the right memory, questions | 94 % / 94 % | 94 % / 94 % | 93 % / 94 % | – |
| computing the meaning vectors | 453 / 1,827 s | 730 / 2,437 s | – | – |

What got worse: recall no longer adds by itself a memory the words didn't find, so paraphrases in recall go from 29 % to 9-11 % (search still finds 53-55 % of them first). The first recall right after the meaning service starts takes ~0.2 s.

### Faster for everyone
- **Every `omoi` call no longer flushes the database's write-ahead log on exit.** On Windows, when the recall hook was the last process with the database open (the normal case without the meaning service), SQLite moved the log into the database and synced the disk on every prompt: recall took ~170-270 ms in 1.1 and 1.2 with the meaning model off, not the ~35 ms measured with another connection open. Now it takes ~30 ms. About once every ~240 prompts one call pays the flush (~0.5 s). The `-wal` file (up to ~4 MB) stays next to the database: Omoikane's own copies (`omoi backup`, the daily copy, `omoi export`) are unaffected, but a database copied by hand needs its `-wal` too.
- Faster process start on Windows (17.4 → 13.5 ms): the home folder comes from the standard library, and the TUI's libraries load only when the TUI opens.

### The meaning model: light and only when it helps
- **The meaning model comes in with the size of the memory.** Below 1,000 memories (every memory in the database counts, so the decision is the same from every folder) Omoikane works as 1.1 did: words and the light model, no download, no service. Once the memory passes 1,000, Omoikane downloads the model in the background, indexes the memories and says so once at the start of a session. The Claude Code plugin and the one-line installers no longer download it. `omoi model semantic --on` uses it with a small memory, `--off` never, `--auto` lets the size decide again; `omoi model semantic` and `omoi doctor` say whether it is in use and why. 1,000 comes from the measurements: with 1,000 memories the model already finds 36 % of paraphrases first in search (8 % without it) and takes recall noise from 30 % to 22.5 %; below that, recall doesn't gain and the download isn't worth it (`OMOIKANE_SEMANTIC_THRESHOLD` changes it).
- **Recall asks the meaning model only to keep quiet.** Only when the words already brought something, on a prompt of more than five words and at most 300 characters, and only to take out what isn't among the three memories closest in meaning. On 1,161 of the author's real prompts it is asked on 60; on the public benchmark (3,000 memories) recall injects something on 7.5 % of the questions with no answer, as in 1.2. It no longer adds a memory the words didn't find (search still finds paraphrases).
- **Preferences are never vetoed**: a preference applies without resembling the prompt ("open it in Creality Print" and the preference of not using Orca). On the author's real prompts, a quarter of the vetoed preferences were useful.
- **When the model doesn't answer in time**, recall goes on with words, as before, but it is no longer silent: `omoi doctor` shows how many times recall asked it and how many got no answer, with the last one. `OMOIKANE_TRAZA=1` writes every step of a recall to stderr.
- **Search can come back empty.** What only meaning brings, with no word in common with the query, needs a similarity of 0.35. With 1.2 a search never came back empty and often showed something unrelated first; now that happens on 6 % of the author's prompts instead of 21 %, with the same first results on the public benchmark.
- **A procedure needs more than one loose word.** "publish a post on LinkedIn" brought "Publish a release" because `publish` is in its `when:` line. Now a single word only brings it inside its own project, or with a word of its title or project ("publish the release", "publish omoikane"); a phrase from `when:` or two of its words still bring it anywhere.
- **Its own engine**: the meaning model runs on f16 weights read straight from the mapped file (AVX2), with a compiled tokenizer. The service is ready in ~26 ms instead of 1.4 s and uses ~13 MB of its own RAM instead of ~490 MB; a vector takes ~21 ms instead of ~42 (16 tokens). Same vectors (cosine 1.000000). CPUs without AVX2 keep using candle.
- **Indexing in batches that give way**: vectors are computed in batches that pause while a query is being served (a query during indexing: 66 ms instead of ~300), up to 3.8× faster per memory, with a RAM cap: `omoi model semantic --ram <MB>` (default 128 MB, minimum 80; `OMOIKANE_SEMANTIC_RAM` overrides it), shown by `omoi model semantic` and `omoi doctor`.
- **The service compares the vectors itself**, kept in memory, so recall and search no longer read every vector from the database on each call.

### Compatibility
- Same as 1.2.0: the database schema (10), the sync lines and the export format don't change. The recall counters go in the local `meta` table, and the compiled tokenizer (`tokenizer.omoi`) is generated locally next to the model; the published model files and their SHA-256 don't change. Checked against 1.0.0 on every commit.

## 1.2.0 (2026-11-01)

Omoikane understands what you ask with other words. Until 1.1, a question that didn't share words with the memory that answers it almost never found it, and engram 3.6 doesn't either. 1.2 adds a second model, EmbeddingGemma 300M, for meaning.

### Measured
On the public benchmark ([omoikane-bench](https://github.com/marcmayol/omoikane-bench), 250 questions written blind), with 3,000 and 10,000 memories:

| | 1.2 | 1.2 with the meaning model off (as 1.1) | engram 3.6, best mode |
|---|---|---|---|
| right memory first, paraphrases | **55 % / 53 %** | 9 % / 8 % | 6 % / 4 % |
| right memory first, questions | **89 % / 88 %** | 85 % / 84 % | 71 % / 71 % |
| right memory first, keywords | 96 % / 94 % | 94 % / 92 % | 88 % / 86 % |
| recall injects something on a question with no answer | **8 % / 15 %** | 40 % / 70 % | – |
| recall brings the right memory, questions | 94 % / 94 % | 93 % / 94 % | – |
| search, P50 | 101 / 126 ms | 37 / 45 ms | 205 / 337 ms |
| recall, P50 | 99 / 126 ms | 35 / 40 ms | – |

What it costs: about 60 ms more per search and per prompt, about 450 MB on disk, and computing each memory's vector once (about 0.25 s each on 8 CPU threads, in the background). Not measured yet at 100,000 memories.

### Added
- **The meaning model**: EmbeddingGemma 300M in pure Rust (candle), with no ONNX Runtime or anything else outside the binary. It gives the same vectors as Google's reference (cosine 0.999 or better, up to 2,048 tokens). It is installed in a compact format of about 450 MB, with its 262,144-token table in int8 read straight from disk, so it loads in 1.4 s. `omoi model install --semantic` downloads it (from [Hugging Face](https://huggingface.co/natzx94/embeddinggemma-300m-omoikane), or this repo's Releases if that fails) and checks every file's SHA-256; `--from` takes it from a folder, and converts the one sentence-transformers leaves. The Claude Code plugin and the one-line installers download it by themselves, once, unless it was turned off.
- **It lives in a service of its own**, one per user, that Omoikane starts by itself the first time it's needed (`127.0.0.1` only, with a token) and that closes after 30 minutes without use. Whoever asks never waits for it to load: without the service, everything works as in 1.1.
- **Vectors computed in the background**: the service computes the vectors a database is missing when it is idle, and every change tells it. They live in a local table that is not synced and that 1.0 ignores. `omoi doctor` shows how many memories have one.
- **Search joins words and meaning**: each candidate scores its similarity in meaning plus a share of its word score. Short queries (five words or fewer, keywords) give words more weight.
- **Recall uses meaning to keep quiet**: what the words bring stays out if it isn't among the three memories closest in meaning, and the closest one comes in when it clearly stands out from the second. Both thresholds are relative (a position and a lead, not a fixed similarity), because similarity changes with the language and with how people write: in the benchmark the right memory sits around 0.7; in real prompts in Spanish with typos, around 0.35. Checked by hand on the author's last 300 real prompts: 5 change, all for the better.
- `omoi model semantic --off` turns it off and closes its service: Omoikane goes back to the light model only, as in 1.1, faster and with less memory. `--on` turns it back on; `OMOIKANE_SEMANTIC=0` overrides both.

### Compatibility
- Same as 1.1.0: the database schema (10), the sync lines and the export format don't change. The meaning vectors are a new local table (`memory_sig`) that 1.0 opens and ignores; checked against 1.0.0 on every commit.

## 1.0.0 (2026-10-31)

The 0.20.0 work, published as 1.0. From here on, 1.x only adds.

### Added
- **Projects and spaces.** Schema 10 turns projects and spaces into tables. A project is found by its git `origin`, so clones, worktrees and moved folders are the same project. A space groups the projects of one client: from a project you see its memories, its space's and the global ones, never another space's. `omoi space add|list|assign|unassign` and `omoi projects list|move|merge|keep|prune`; `project` and `space` in `search`, `recent` and `remember`, still with the same 8 tools.
- **One repository per client.** `omoi sync init --space acme <url>` gives a space its own repository and key: it carries only that space, and accepts only lines of that space. Nothing of one client reaches another's repository or the general one.
- **Key rotation.** `omoi sync rotate` creates a new key, re-encrypts this computer's lines and gives the new code. Whoever only has the old key stops reading what's new. Every line carries the id of its key (`k2:…`; lines without a prefix are key 1, as before).
- **The space of a project travels.** Moving a project to a space reaches the other computers of the same person. A line that says a project is in another space never moves it: at most it pauses the project until the person decides here (`omoi projects keep` or `omoi projects move`), with a notice in `sync`, `sync status`, `doctor`, `review`, the web view and the session start.
- **Formats that 1.x can extend.** Unknown fields in sync and export lines are kept and passed on (`extra`). Lines of an unknown type are counted apart from unreadable ones and read again after updating. A repository can ask for a newer reader (`omoikane.format`, encrypted), and an older `omoi` then leaves it alone. A database records the oldest schema that can read it (`lector_minimo`).
- Copy of the database before migrating (`VACUUM INTO`), and an incremental detector of outdated memories.

### Fixed
- Isolation between people and between clients, reviewed in five independent passes with scripts against local git repositories: `dir:` keys always carry the person, forgets, verdicts and exports never cross from one space to another, a `project` line from someone else only pauses, and a client's repository can't claim a project in advance.

### Measured
- With 50,000 memories: `remember` 294 ms (0.19.1: 2.5 s), `update` 263 ms, `omoi sync` with no changes 1.98 s (same as 0.19.1), recall as before. 219 tests on Windows and Linux.

### Compatibility
- **Promise for all of 1.x:** the database, the sync lines and the `omoi export` format don't change in any way that breaks a 1.0. A 1.0 keeps and passes on what it doesn't understand, steps away from a repository that asks for a newer reader, and opens a database that only adds. The 8 tools and their parameters don't break. Anything a 1.0 would misread (a new scope, for example) raises `min_reader` and needs the newer version.
- **Opens** databases from any 0.x and migrates them to schema 10 on first use, after a copy. **Reads** sync repositories and exports from 0.x.
- **0.19.x and earlier** can't open a 1.0 database, and don't understand a repository after a key rotation or one with spaces. Update every computer that shares a repository.
